## Problem Background

The problem related to data science — predicting future values to make better decisions using historical data in distributed computing — is the topic of resource usage prediction for autoscaling. Resource usage prediction for autoscaling is used to predict future CPU, memory, and I/O utilization so resources can be scaled proactively, rather than reacting after a failure occurs. If we give a workload too little, it slows down or crashes. If we give it too much, we waste resources and money. If we can predict the future demand for resources, then we can give each workload the right amount at the right time and will prevent failure due to resource has threshold from happening.

Cloud operators and platform engineers who run applications on distributed systems like Kubernetes (automates the scaling and management of containerized applications) experience this problem. They manage large numbers of workloads that each require CPU, memory, and I/O resources. They want to give each workload the right amount of resources — too little leads to slowdowns and crashes, while too much leads to wasted cost and capacity. It is currently done with a reactive method, in which the system watches resource usage and only adds resources when CPU or memory crosses a threshold. This is inefficient when many different workloads must be managed. The limitation is that by the time the system reacts, the problem has already occurred. This problem matters because it costs money and hurts users' experience when workloads receive the wrong amount of resources needed. The problem occurs under conditions where resource demand changes so quickly that the system is unable to react, especially with unpredictable workloads.

Reactive autoscaling is structurally lagging, with a three-to-five-minute timing period spent waiting to scale resources after the threshold is breached. During this window, it leads to tail-latency degradation (the slowest performance) and service-level objective (SLO) violations. This claim is supported by Tran, Duy Anh as documented source. Conventional autoscaling, which is a reactive method, scales workloads based on the resource utilization of CPU and memory, which can lead to a failure to anticipate the burst demand of these workloads. This means that with the reactive method, the resources used for certain workloads cannot handle the burst demand for immediate changes in resources to achieve better performance. This claim is supported by Karthik Chakravarthy Cheekuri as documented source. With sudden load spikes, Horizontal Pod Autoscaler will trigger the threshold and wait for the new resource, which can cause cold starts, temporary under-provisioning, and frequent SLO violations. This claim is supported by Hyunsu Jeong and others as documented source.
